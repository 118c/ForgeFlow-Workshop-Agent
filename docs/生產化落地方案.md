# ForgeFlow 生產化落地方案

> 實作狀態（2026-09-10）：PostgreSQL/SQLite 雙剖面、Redis 協調、Celery 任務佇列、Transactional Outbox、五系統版本化契約、CP-SAT、歷史回放與單車間灰度控制已落地。SSO/RBAC、完整可觀測性及正式產線驗收仍屬後續工作。

## 一、目前成熟度判斷

目前版本是可運行、可聯調的車間作業規劃服務基線，具備五節點編排、串流事件、業務閘道、多模型降級、任務快照、人工審核及 MES 下發邊界。

但它還不能直接被稱為真正的產線生產系統，主要差距不是畫面，而是以下條件尚未由真實環境驗證：

- CP-SAT 已涵蓋物料、治具、換線、工序前後置、設備維護窗口及人員技能，仍需以工廠主資料校準轉移批與求解參數；
- 本地剖面仍使用 SQLite；企業剖面已支援 PostgreSQL、Redis 與 Celery，但尚未完成容量及災難復原驗證；
- 已定義 MES、WMS、EAM、HR 與 QMS 標準契約，尚待目標工廠確認欄位映射與資料品質基線；
- 尚未實作企業身分認證、角色權限、資料分級、金鑰託管及不可竄改審計；
- 尚未以歷史排程與實際完工資料驗證交期達成率、換線次數、設備負載及求解時間。

因此，對外最準確的定位是：**具備清晰生產化路徑的車間作業規劃平台基線**。

## 二、目標生產架構

```text
排程主管 / 線長 / IE 工程師
              │ SSO + RBAC
              ▼
        API Gateway / WAF
              │
       ┌──────┴──────┐
       ▼             ▼
FastAPI 無狀態服務   SSE/WebSocket Gateway
       │             │
       └──────┬──────┘
              ▼
       任務佇列 / 工作節點
              │
       LangGraph 工作流程
  資料快照 → 約束校驗 → CP-SAT 求解
       → LLM 解釋/風險 → 人工審核
              │
     Transactional Outbox
              ▼
           MES 下發

PostgreSQL：任務、版本、審計、Graph Checkpoint
Redis：冪等鍵、短期快取、分散式鎖、熔斷狀態
Kafka/RabbitMQ：任務事件、設備事件、下發重試
Prometheus + OpenTelemetry：指標、日誌、Trace
```

核心原則：LLM 不直接決定不可逆的生產動作。它負責自然語言約束抽取、異常解釋、風險摘要及方案問答；可行性由約束校驗器與求解器保證，最終下發由人工審核與權限策略控制。

## 三、分階段建設

### Phase 1：產品可信度補強（可直接在目前倉庫完成）

目標是讓系統形成覆蓋規劃、審核、追蹤與資源治理的完整業務工作台。

1. **任務中心**：最近任務、狀態篩選、建立人、車間、版本、失敗重試與批次取消；
2. **審核中心**：待辦清單、修改前後差異、審核意見、雙人覆核策略及逾時升級；
3. **資源中心**：設備狀態、OEE、維護窗口、班組技能矩陣及資料最後更新時間；
4. **方案版本比較**：比較交期、負載、加班、換線與風險，支援選定某一版本下發；
5. **運行追蹤**：以 `trace_id` 顯示節點輸入摘要、輸出摘要、耗時、降級原因及模型供應商；
6. **操作稽核**：建立、重排、修改、核准、退回、下發與重試全部形成時間線；
7. **國際化**：繁中為預設，簡中與英文完整覆蓋，API 錯誤碼與畫面文案分離；
8. **資料集管理**：內建資料只由管理員設定，業務頁面不出現測試語意。

這一階段可顯著提高產品完整度，且不需要預設尚未經真實環境驗證的企業介面或生產數字。

目前進度：任務中心、審核待辦、資源台帳、方案版本比較、運行 Trace、基礎操作稽核及三語介面已完成。資源資料帶來源版本與擷取時間，方案比較保留歷史修訂並計算準時率、負載、加班、換線及風險差異；雙人覆核策略與管理員資料源設定仍待下一階段實作。

### Phase 2：真實資料契約與數位影子

先接「只讀」資料，不立即下發，讓系統在真實資料上以影子模式運行。

- MES：工單、工藝路線、計畫狀態、實際開完工；
- WMS：物料齊套時間、缺料、批次與倉位；
- EAM/設備平台：能力、狀態、故障、保養窗口與 OEE；
- HR/排班：班次、到崗、技能證照與加班上限；
- QMS：首件、抽檢、不良率與返工約束。

每個來源需要 OpenAPI/AsyncAPI 契約、欄位字典、時區規則、主資料 ID 映射、超時策略及契約測試。資料快照應帶 `source_version` 和 `captured_at`，確保事後可以重現某次排程。

### Phase 3：約束求解核心

以 OR-Tools CP-SAT 建立正式求解器，啟發式規則保留為快速方案和故障備援。

硬約束必須 100% 滿足：

- 工序先後與最短等待時間；
- 設備/工位能力、可用日曆及保養窗口；
- 人員技能、班次與法定工時；
- 物料齊套、治具/模具互斥；
- 批量上下限、線體相容性與不可拆工單。

軟目標採可配置權重：交期延期、換線時間、加班、在製品、設備負載均衡與能耗。求解器設定時間上限，超時返回當前最佳可行解，而不是讓 HTTP 請求無限等待。

LLM 可將主管輸入的「A17 優先、盡量不加班」轉成候選約束，但必須經結構化校驗和人工確認後才進入求解器。

### Phase 4：平台可靠性與安全

- PostgreSQL 持久化任務、版本、審核與 LangGraph Checkpoint；
- Redis 保存冪等鍵、快取、分散式鎖與跨實例熔斷狀態；
- 工作佇列隔離長任務，API 只負責建立任務與訂閱事件；
- Transactional Outbox 確保「審核已落庫」和「MES 最終下發」一致，支援重試與死信處理；
- OIDC/AD 單一登入，按工廠、車間、角色做 RBAC；
- Vault/KMS 管理密鑰，服務間使用 mTLS，敏感欄位遮罩；
- 所有人工與系統操作保留不可修改的審計事件；
- 多副本部署、健康探針、滾動升級、資料備份和災難復原演練。

### Phase 5：影子驗證與灰度上線

1. 回放最近 8–12 週歷史資料，確認所有方案可行；
2. 與人工計畫做盲測比較，不影響現場；
3. 在單一車間只提供建議，由主管人工轉錄；
4. 啟用受控 MES 下發，但保留原排程系統一鍵回退；
5. 指標達標後逐步擴展到其他線體。

## 四、建議驗收門檻

| 維度 | 建議門檻 |
|---|---|
| 可行性 | 硬約束違反率必須為 0 |
| 排程效能 | 常規日計畫 P95 求解時間 ≤ 60 秒 |
| 服務可靠性 | 月可用性 ≥ 99.9%，任務可恢復率 100% |
| 資料品質 | 關鍵主資料完整率 ≥ 99.5%，來源可追溯率 100% |
| 下發一致性 | 審核後計畫零重複、零遺失，可安全重試 |
| 安全 | 未授權下發為 0，關鍵操作審計覆蓋率 100% |
| 業務成效 | 以影子期基線驗證 OTIF、換線時間與加班時數，不預設虛構百分比 |

## 五、推薦下一輪實作順序

若以「產品可信度 + 未來真實可用」共同排序，建議：

1. 先完成任務中心、審核中心與 Trace 詳情，讓目前已有 API 真正被產品介面使用；
2. ~~新增 PostgreSQL、Redis 與 Outbox，建立可靠的狀態和下發語義；~~（已完成基線）
3. ~~建立標準 MES/WMS/EAM/HR/QMS 契約與可配置資料映射；~~（已完成基線）
4. ~~引入 OR-Tools CP-SAT，逐項補齊工廠約束；~~（已完成基線）
5. 完成 SSO/RBAC、觀測告警與正式產線驗收。

不建議優先增加更多 Agent 或更複雜 Prompt。對生產系統而言，資料契約、約束可行性、審核權限和下發一致性，比 Agent 數量更能證明工程能力。
